# Release notes — v1.3.6

Released 2026-07-19.

**Compare range:** https://github.com/Swamp-Ig/pizone/compare/v1.3.5...v1.3.6

This is a **pre-release** for integrators (especially Home Assistant Phase 2
work). It is not aimed at end users as a standalone upgrade. Prefer waiting for
a future stable line unless you are developing against the new discovery API.

## Since v1.3.5

- Discovery scan wait (`SCAN_TIMEOUT`) reduced from 20s to 5s
- `close()` waits until the UDP transport has finished tearing down before
  returning, so a following `create_discovery()` can rebind `:7005` immediately
  (fixes delete → HomeKit rediscovery `EADDRINUSE` races)
- Failed `create_discovery` / `start_discovery` no longer leaves a sticky
  process singleton that blocked retries until process restart
- `PLACEHOLDER_DEVICE_UID` is no longer exported from the public package API
  (`UnpairedBridgeError` remains the supported signal)

Everything from v1.3.5 below still applies.

## Summary (since v1.3.4)

- HTTP connections are closed after each GET, which greatly reduces stalls on
  some iZone bridges ([home-assistant/core#176536](https://github.com/home-assistant/core/issues/176536))
- A new discovery and refresh API is available for integrators (the older API
  still works for now)
- iPower monitoring is off unless you opt in with `ENABLE_POWER = True`
- Bridges that are not paired to an air conditioner (UID `000000000`) are
  ignored or rejected instead of showing up as broken controllers
- Faster discovery scans and reliable UDP close → recreate (this release)

## Bridge connection reliability

Some ASH bridges misbehave when HTTP connections are reused. This release
line:

- Sends `Connection: close` on every HTTP GET (polling and discovery probes)
- Closes TCP connections after each request when the library creates its own
  aiohttp session

This reduces how often the bridge stops responding. It does not fix every
hub-side stall; replacing faulty hardware may still be needed.

## New discovery and refresh API (optional for now)

Integrators can adopt a clearer model without background poll loops inside the
library:

- `create_discovery()` with callbacks when a controller is found or its IP
  changes
- `discover_by_host`, `discover_by_uid`, `discover_all` to find bridges on the
  network
- `create_controller(uid, host)` to connect to a known bridge
- `refresh_all`, `refresh_system`, `refresh_zones`, and related methods so the
  caller controls when to poll

`close()` on the discovery service now waits for UDP teardown so the next
`create_discovery()` can bind the discovery port again without racing the OS
socket release.

The previous API (`discovery()`, `fetch_controller`, `Listener`, and so on)
still works.

## iPower opt-in

`ENABLE_POWER` now defaults to `False`. Power monitor HTTP traffic only runs
after you set `pizone.ENABLE_POWER = True` before creating or refreshing a
controller. This avoids extra requests on bridges that advertise iPower but are
not set up for it. The default may change if more field data shows power
monitoring is reliable enough to enable by default.

## Unpaired bridges

Wireless ASH bridges with no AC paired report device UID `000000000`. The
library now:

- Ignores them during passive UDP discovery
- Raises `UnpairedBridgeError` if you try to connect to that UID on purpose
- Refuses to cache them after an IP lookup

Paired bridges that temporarily report fault-shaped settings (AC off, reboot,
and so on) are unchanged: they keep their real UID and show as disconnected
until the AC data recovers.

## Other changes

- UDP `CHANGED_*` notifications are recognized and ignored (no spurious refresh)
- Discovery verifies bridge identity over HTTP before trusting UDP replies
- Development tooling moved to Ruff for lint and format

## Home Assistant

Pin `python-izone==1.3.6` when adopting the Phase 2 discovery / coordinator
runtime. This pre-release is intended for that integration work, not as a
general end-user library upgrade on the legacy path alone.
