# Release notes — v1.3.5

Released 2026-07-17. **Beta release** for the upcoming Home Assistant iZone
Phase 2 integration work (izone 1.4 program). The version number stays on the
**1.3.x** line for now; the program name is “1.4” internally.

**Compare range:** https://github.com/Swamp-Ig/pizone/compare/v1.3.4...v1.3.5

## Beta status

This release ships the full dual-track library on `main` so Home Assistant can
pin a real PyPI version while Phase 2a/2b land. The **current HA integration
still uses the legacy API** (`discovery()`, `fetch_*`, `Listener`). The new
consumer-driven API is available for new integration code but is not required
for a pin-only HA bump.

**`1.4.0`** (planned after HA Phase 2 merges) will remove the legacy surface
(`discovery()`, `fetch_*`, `Listener`, and related poll/scan loops).

## Summary

Since `v1.3.4`, this release adds the izone 1.4 discovery and refresh model
alongside the legacy path, gates iPower behind an opt-in flag, rejects
unpaired-bridge placeholder UIDs, and mitigates HTTP keepalive stalls on some
ASH bridges.

## Connection: close (core#176536)

- HTTP **GET** requests send `Connection: close` (controller reads and
  discovery probes)
- When pizone owns the aiohttp session, `TCPConnector(force_close=True)` is used
- Mitigation for hubs that stall under connection reuse; does not fix hub-side
  stalls reported in [home-assistant/core#176536](https://github.com/home-assistant/core/issues/176536)

## New 1.4 API (dual-track — beta)

Available now; legacy path remains for existing consumers:

- **`create_discovery()`** — one-shot discovery service with callbacks
- **`discover_by_host`**, **`discover_by_uid`**, **`discover_all`** — ephemeral
  or service-scoped endpoint discovery with HTTP verify
- **`create_controller(uid, host)`** — explicit controller factory after
  discovery
- **`refresh_all`**, **`refresh_system`**, **`refresh_zones`**, etc. —
  consumer-owned polling on the 1.4 path (no library debounce loops)
- **`ControllerEndpoint`**, **`on_endpoint_discovered`**, **`on_address_changed`**
  callbacks for integration discovery flows

Legacy **`discovery()`**, **`fetch_controller`**, **`fetch_controllers`**, and
**`Listener`** continue to work unchanged on the deprecated pathway.

## Power gate

- **`ENABLE_POWER`** defaults to **`False`**; no iPower HTTP I/O until set at
  runtime (for example `pizone.ENABLE_POWER = True` before create/refresh)
- Home Assistant does not expose power entities yet; this avoids surprise I/O on
  bridges that advertise iPower in UDP

## Unpaired bridge UID

- **`PLACEHOLDER_DEVICE_UID`** (`"000000000"`) — exact match for ASH bridges
  with no paired AC
- Passive UDP discovery ignores this UID (no cache, no notify)
- **`discover_by_uid`** / **`create_controller`** reject immediately with
  **`UnpairedBridgeError`** (no network I/O)
- **`discover_by_host`** raises after HTTP probe if the UID is the placeholder
  (no cache)

## UDP and discovery (1.4 path)

- **`CHANGED_*`** push datagrams recognized and ignored (no refresh)
- ASPort passive discovery caches unclaimed endpoints and fans out
  **`on_endpoint_discovered`** for new or host-changed endpoints
- **`discover_all`** HTTP-verifies collected hosts and dedupes notifications

## Other

- Live fault-shaped **SystemSettings** fixtures for unpaired and paired cold-restart
  specimens (tests)
- Test suite labelled with disposition comments (`1.4` vs `deprecate`) for
  dual-track cleanup
- Ruff replaces Black and pylint for lint and format

## For Home Assistant integrators

Pin **`python-izone==1.3.5`** for:

1. **Immediate:** Connection: close mitigation on the existing legacy integration
   path (pin-only bump)
2. **Upcoming:** Access to the 1.4 API when Phase 2 runtime and config flow land

Do not expect breaking changes on the legacy API until **`1.4.0`**.
